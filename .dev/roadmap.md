## Phase 3: personal context portability

Goal: a user can maintain a private GitHub repo mirroring their `~/.claude/` global setup (CLAUDE.md customizations + global memories), so that switching to a new Claude account doesn't erase accumulated rapport and preferences.

Design sketch:
- User creates a private repo (e.g. `<user>/claude-context`) following a structure agentics defines
- Suggested structure: `CLAUDE.md` (global instructions snapshot), `memory/MEMORY.md` + memory files, optionally `projects/<project>/memory/` for project-specific memories
- agentics provides: template for the private repo structure, a standard bootstrap prompt the user gives a fresh agent to reconstitute context from the private repo, guidance on what belongs there (preferences, feedback patterns, working style) and what does not (credentials, project-specific ephemera, anything derivable from code)
- Sync discipline: end-of-session or on-demand; the user commits manually: no automated push

Open questions:
- Should agentics include a `template/personal-context/` scaffold, or document the pattern only in prose?
- How does the bootstrap prompt discover which projects to also load memories for?
- Where does the private repo live relative to agentics in the contribution/update-propagation model?

## Design questions: needs more thinking

- **Startup instruction-file integrity check:** at session start, run `git log --oneline -- CLAUDE.md AGENTS.md` and flag unexpected changes not made by the repo's lead developer; useful tamper signal but adds a mechanical step: decide whether this is a hard rule, optional guidance, or a softeng-specific convention
- **Context sync across projects:** the upstream-update check (`convention-levels.md` § Checking for upstream updates) now surfaces drift automatically for opted-in projects, but the "source of truth" ownership model is still informal: which conventions are global, which are template, which are project-specific, and how to reason about overlap when a project has genuinely diverged on purpose

- **Integration with existing agent setups:** the current approach (initialization question + "supplementary" flag) is minimal; deeper questions remain: should the agent offer to review existing conventions for conflicts? How prescriptive should softeng conventions be when a rich setup is already in place? Is "supplement on conflict" even the right default, or should users choose a merge strategy?
- **Non-softeng users:** the general layer already serves anyone, but the template flow and README still implicitly frame softeng as the "extra" and everyone else as the base case; explore whether the initialization flow, framing, and contribution model should be more explicitly welcoming to teams outside softeng adopting the pattern wholesale
- **Dev vs. non-dev users:** the template currently assumes a developer audience (code reviews, test conventions, OWASP); consider a third initialization question: "Do you work primarily in code, or in planning/documentation/research?" and distinct dispatch paths or convention sets for each. One piece of this is now done, prompted by a real incident where a docs-only session never saw the commit-attribution rule since it lived in a code-scoped file: `code-style.md` was split so only dev-only implementation conventions remain there; the universal sections (dashes, spelling, typos, property ordering) moved to a new `conventions/writing-style.md`, and the Git section (commit safety, no AI-tool attribution) folded into `session-discipline.md`, both read unconditionally by everyone. Still open: the initialization question itself, and whether session discipline should be lighter for a non-dev role
- **Response verbosity/tone calibration per role:** distinct from the item above, which is about which conventions load. This is about how the agent talks once it's using them. A session working through the upstream-update-check design was appropriately thorough for a dev/AI-eng/contributor audience (file diffs, precedence mechanics, why something changed): the same level of detail would read as noise to a general (non-dev) user, who likely wants outcomes and next steps with detail available on request, not by default. `CLAUDE.roles/*.md` currently shape *what* applies per role, not *how verbose or technical* the agent's own responses should be for that role; needs its own dispatch, probably as a short section per role file rather than a new mechanism. **A second, mode-based axis, independent of role:** noticed directly in a design/planning session, not reported secondhand: a lengthy, comprehensive response during active back-and-forth design work gets partially skimmed and disregarded rather than fully read, and the user responds anyway, continuing the conversation around what the response missed. The response was trying to be thorough, but the actual effect was a longer, more interactive exchange than a shorter, more focused one would have produced, the opposite of what thoroughness was meant to achieve. This applies even within a single role/audience: a dev/contributor session in active design mode still wants short, reply-inviting turns, not comprehensive up-front coverage, the same instinct that overwrites the role-based calibration above rather than composing with it. Unsolved part: reliably detecting "active design/planning conversation" as a mode, distinct from "reporting completed work" or "final review," the same kind of detection problem session-start signals took iteration to get right
- **"Modality" as a general interaction-mode framework:** parked here deliberately, not designed, so it isn't lost. Human collaborators enter different mental modes depending on task, personality, and ability. "Collaboration" (planning, workshopping, brainstorming: back-and-forth, not user-issues/agent-executes) is one instance already being worked out, see the "Response verbosity/tone calibration" item above. Others named so far, not defined: "learning" (varies by learning style, resists generalization), "documenting" (user-heavy collaboration, already observed in practice; this very entry is an instance of it). "Imperative" (bare commands) is not itself illegitimate: a concise instruction can still carry full purpose and intent. The actual failure mode is a command issued with no regard for plan, purpose, or intent at all, which "verify purpose alignment before implementing" (`code-style.md`/`AGENTS.md` Interaction parameters) already exists to catch from the agent's side. Whether "modality" becomes its own detection mechanism, reusing the explicit-phrase-plus-inferred-signal-plus-confirm pattern from collaboration mode, or stays a loose descriptive frame, is undecided
- **Project memory hygiene: pruning locally-superseded items.** Resolved into two different fixes, not one, since adopters and contributors go stale for different reasons and at different rates. A real audit of agentics' own memory (2026-07-30) found four separate personal-project memories each explicitly noting they'd already been "independently codified" into agentics itself, none ever pruned, plus two memories misfiled under the wrong project entirely. For an ordinary adopter, staleness happens when agentics ships something new that happens to formalize what they'd noted informally, an event they only learn about via the upstream-update check: `convention-levels.md` § Checking for upstream updates' classification step (6) now also checks whether a new entry formalizes something the project's own memory already tracks informally, and prunes it there. For a contributor, the staleness is self-inflicted in the same breath, shipping the convention *is* the event that makes the memory redundant, so waiting for a separate audit misses it every time: `CONTRIBUTING.md` § Proposing changes now has a step (8) to prune or trim the relevant memory immediately after shipping the convention that superseded it, not later
- **A "vault" pattern for memory: content isolated behind a passphrase, not just an instruction to keep it private.** Raised while discussing memory hygiene generally: a behavioral "don't surface this unless asked" flag on a memory entry isn't real isolation, it depends on every future agent instance actually honoring the instruction, and does nothing against direct file access. Three distinct tiers, not one mechanism: (1) a behavioral gate, cheap, no tooling, what exists today via a flagged description on an entry; (2) exclusion from the auto-loaded memory index (`MEMORY.md`), so a vault entry is never pulled into context unless something specifically goes looking for it; (3) actual encryption at rest, using a vetted tool (`age -p`'s passphrase-based symmetric mode is the simplest fit, not a homebrew cipher), decrypted only via a deliberate step where the developer supplies the passphrase fresh in that session, never persisted anywhere. Two caveats worth keeping attached to this idea rather than losing in a later summary: a memorable passphrase isn't automatically a secure one, the protection is bounded by how unguessable the specific sentence is, not how easy it is to recall; and encryption at rest can't retroactively protect content already spoken plainly earlier in the same conversation. Not yet decided: whether this becomes a documented, generic memory-hygiene pattern any adopter could use across their own project/personal/global memory scopes, or stays an individual practice; and, if generalized, how the decrypt step would actually be specified as a repeatable convention rather than one-off improvisation.
- **Roadmap done/not-done separation:** `session-discipline.md` § Keeping `.dev/` current (and this file's own header) currently has completed roadmap items removed entirely rather than kept anywhere. Consider relocating finished items to a separate "Done" section after the open ones instead of deleting them, so recently-finished work stays visible without cluttering the open list. Ordering (within the done section, and relative to the open one) needs more thought before this is a concrete rule
- **Coding conventions proposed for later discussion, not yet agreed:** a colleague proposed the following for `code-style.md`, applicable to code review, PR review, and code produced from design sessions alike. Not adopted: discuss and decide before adding any of these.
  - No `Type` suffix on type names, no `I` prefix on interfaces: descriptive names only (`ThemeContext`, not `ThemeContextType`); interface and type names look the same either way
  - Declare return types explicitly on named/declared functions; anonymous functions passed as arguments may omit them
  - Full-word, descriptive variable names always, never a single letter or an abbreviation (`props` not `p`, `count` not `i`)
- **Definition of done: a completion checklist, universal and project-specific.** Two levels of the same underlying gate. Universal, fixed categories applying to any project: tests (`testing.md`), in-code documentation including comments where the WHY is non-obvious (`code-style.md`'s Comments and TSDoc rules), `/docs` or equivalent external-facing docs if the project has them (`documentation.md`'s two-tier model), `.dev/` (`session-discipline.md`'s existing "Keeping `.dev/` current"), `CHANGELOG.md` if the project keeps one, the same "Unreleased" discipline agentics applies to itself, and a final refinement pass over both the docs and the changes themselves before calling anything done (`session-discipline.md`'s existing "Refinement passes: not just once at the end," named here as the last gate rather than a separate new mechanism). Five of these six already have their own convention individually; what's missing is the single completion gate tying them together, so a change doesn't get called done while one of the six quietly lagged behind unnoticed. Project-specific, open-ended checklists keyed to a recurring task *type*, not a universal category: in Arranger's `search-server`, adding a new env var should also update `.env.schema` and the README's env var table; a different project's recurring task types and the artifacts each touches will differ entirely, so agentics can only template the *pattern* for a project to document its own, not the checklists themselves. One question already resolved: the developer pointed out that "is this done?" is literally an instance of "the ultimate question," the same adversarial search stance `AGENTS.md`'s "Default review or audit posture" bullet already names, just asked at the completion checkpoint specifically. That bullet now lists "is this done?" as a recognized trigger phrase alongside "does this look okay," so once this checklist exists, asking it is what invokes checking against it, not a separate mechanism.

Still needs shaping: where either level lives in `AGENTS.md` (a new section, cross-references added to each existing file, a dedicated place for the project-specific level); how an agent recognizes it's doing a checklisted task type in the first place for the project-specific level; matching a task to a checklist entry is itself a recognition problem, the same one session-start signals and sanity-check phrasing already solve differently for other triggers.
- **Research software-based testing options for agentics:** `testing/` currently holds four practice-based verification methods (fixture dry runs, a CHANGELOG-derived regression checklist, cold-read review, a consistency script), not software, since agentics is prose with no compiler or test runner. Worth researching whether an actual eval harness (running an agent against a fixture automatically and checking the outcome, rather than a contributor doing it by hand) is worth building as agentics matures into a more sophisticated system, versus staying practice-based indefinitely. Flagged directly by the developer as a "maybe I'm overengineering this" concern: the four practices already in place don't depend on this landing, so there's no urgency, this is a research question, not a commitment to build
- **Release process convention: source document has landed, not yet ready to template.** `overture/arranger/.dev/docs/release-process.md` is the pattern document the previous version of this item was waiting for; it explicitly frames itself as source material, not the convention itself, and is validated against exactly one real round (2026-07-20) so far, the same "prove it before templating it" bar other roadmap items here hold themselves to. Generalizable patterns worth carrying forward once it's abstracted: a two-tier branch promotion (`main`, code only, frozen placeholder version → an rc-staging branch → the real release branch, each promotion an identical merge-then-bump procedure one level up); version bumps are entirely a release-branch concern, never touched on the code branch, which is why merging code into a release branch never conflicts on the version line; a semver-judgement framework that first distinguishes packages with no real shipped release yet (bump the rc counter freely, no compatibility contract exists to break) from packages with an actual stable baseline (strict semver against that baseline, judged by diffing the exported entrypoint first, then checking real-world consumer exposure before finalizing severity, not just textbook classification); never hand-resolve a generated lockfile's merge conflicts, keep one side and regenerate; a separate merge-commit and bump-commit for independent reviewability; and naming an interim workaround's planned retirement condition explicitly rather than leaving it silently permanent. The document's own § 10 lists five specific open questions to resolve when abstracting it (how far the frozen-placeholder-version convention generalizes, whether the never-released/already-released split needs simplified forms for a brand-new or fully-mature monorepo, whether the two-commit convention holds for squash-merge-heavy teams, stating the lockfile rule package-manager-agnostically, where a CI severity-suggestion tool would belong). Given the scope (branching, versioning, a judgement framework, CI mechanics), this needs its own dedicated design pass, not a fold-in alongside other work.

Scope confirmed: for softeng projects adopting agentics (Arranger as the proving ground), not agentics' own release process, which stays as `CONTRIBUTING.md` already has it. The branching/merging model is the actual documentation target; Jenkins mechanics are ancillary context for how softeng's own CI happens to hook in, not something the convention needs to generalize across CI systems.

Changesets, raised as a candidate for replacing the manual §4/§5 process, checked against its own current docs rather than assumed: a changeset file's frontmatter holds package name → bump *type* only (patch/minor/major), never a version number, so adopting it wouldn't force real version state onto a frozen `main`. The documented, bot-automated workflow assumes changesets accumulate and get consumed on the *same* branch; nothing in Changesets' own docs supports accumulating on one branch and consuming (bumping) on a separate downstream branch the way this design wants, so this was flagged as needing a real prototype rather than trusting the theoretical risk either way.

**Resolved via a real prototype in Arranger** (`.dev/docs/release-process.md` § 9, disposable two-package throwaway monorepo, real `git merge`/`changeset version` runs): the accumulate-on-`main`/consume-on-`release-test` split is not blocked. `changeset version` run on `release-test` alone behaves exactly as documented (correct bump, correct changelog, deletes the consumed file there only); `main`'s copy is untouched. A second round confirmed the predicted reintroduction/conflict problem does not happen in the ordinary case: git's 3-way merge auto-resolves the delete-vs-unmodified difference cleanly, the same mechanism already relied on for the version-field auto-merge (§2 of that document). The one real edge case that does conflict, editing an already-consumed changeset file on `main` after the fact, produces a genuine `CONFLICT (modify/delete)`, trivially fixed with `git rm` on the merge, and cheaply preventable with a CI lint rule blocking edits to pre-existing `.changeset/*.md` files. This clears the compatibility concern; adopting Changesets does not require abandoning the `main`-stays-version-free requirement.

Other resolved-for-now points: the local-exposure-check step (grepping sibling repos on the same machine for consumers) stays pending, revisit only if it becomes a practical problem, not designed preemptively. Validate by building the flow and testing it against repeated real rounds in Arranger directly, rather than requiring more proof before starting. Confirmed this becomes its own new `conventions/*.md` file; whether it needs a single-package/monorepo split, and the exact agent-facing steps, are both left for a later design pass
- **Agent manager: cross-repo agent orchestration, so the developer isn't the messenger.** The developer has repeatedly needed to relay findings and instructions between a session working in one repo and sessions working in others, carrying context back and forth by hand. Explore a formal process for one agent to address or spawn agents working in other project contexts directly, surfacing only what needs the developer's attention rather than the developer serving as the message-passing layer between separate sessions. Undesigned: the actual mechanism (a shared task queue, a supervising session, something else), how results from multiple projects get consolidated back to the developer as one coherent thing rather than N separate reports, and what keeps an "agent manager" from taking action in a project without the same developer review any single session already respects
- **"Nuclear upgrade": an explicit, named, triggerable procedure for syncing every known agentics adopter at once.** Demonstrated ad hoc today: syncing lyric, maestro, docs, infra, helm-charts, usher, and arranger to `0.9.0` in one pass, three done directly, four dispatched as parallel background agents each running the real `upgrading-adoption.md` diagnosis rather than a one-line patch. It worked, but it was assembled in-session, not a documented, repeatable procedure. Needs shaping: where the list of "known adopters" comes from (the developer's own cross-project map § Agentic projects, now that it exists); the actual trigger phrasing; whether every repo gets the full diagnosis or a cheap tag-diff check first with the full diagnosis reserved for stale/no-tag cases, mirroring the per-project logic already in `convention-levels.md`; and how conflicts and abstraction candidates from many repos surface back as one decision queue instead of scattered per-repo reports
- **Root-plus-local `.dev/` hierarchy for monorepos: worth a `session-discipline.md` pattern?** `overture/helm-charts` is piloting a repo-level `.dev/` for cross-chart concerns plus an optional per-chart `.dev/` for chart-specific roadmap/tech-debt/session history, so far only in one chart (`arranger/`) of twelve. `session-discipline.md` currently assumes a single project-root `.dev/`; a monorepo with independently-versioned sub-units (charts, packages, apps) may need this documented as a real pattern rather than each adopter improvising its own shape. Deliberately not designed yet: this is one pilot, one data point; revisit once it's actually proven out or a second project needs the same shape, the same "prove it before templating it" bar the release-process item above already applies
- **Portable agentics for non-repo-access Claude surfaces (claude.ai Projects, custom instructions), low priority.** Agentics' whole mechanism assumes a coding agent with live filesystem/git access (Claude Code, Cursor, Copilot, Aider); a regular claude.ai chat has neither a repo nor persistent file dispatch. Partial analogs exist today (Claude Projects' custom instructions plus knowledge files, for a static uploaded subset; account-level custom instructions for the behaviour-only "Global" tier), but nothing packaged or documented. Explore what a deliberately portable version would look like: which parts translate directly (Interaction parameters, Critical constraints, anything behaviour-only with no file dispatch), which need a different shape entirely (`.dev/` discipline, session logging, and the upgrade-check mechanism all assume a persisting repo and don't obviously translate), and whether this becomes a new template artifact (a condensed single-file version for pasting into a Project) or just a documented adaptation guide. Distinct from Phase 3 above (personal context portability across Claude accounts): this is about porting project-level conventions to a surface with no project or repo at all, not personal preference continuity
- **A concrete bootstrap artifact for a new agentics *contributor*, not just a new adopting project.** `template/README.md` already has a bootstrap prompt for onboarding a new project; nothing equivalent exists for onboarding a new person into contributing to agentics itself, which right now means walking them through `CONTRIBUTING.md` § Agent setup for contributors from memory, an easy step to skip for a brand-new contributor. A short, literal prompt to paste into a new contributor's own agent (setting `agentics_contributor: yes`, recording the Repo URL, running the freshness check once) would make that reliably happen instead of depending on someone remembering to walk them through it by hand
- **Backfilling lessons learned from already-existing artifacts, not just live capture.** `definition-of-done.md`'s lessons-learned criterion and this file's own memory-hygiene entries above both assume capture happens live, at the decision point, in the session that made the decision. Nothing mines what's already sitting in closed PRs, resolved tech-debt entries, or old issue threads for a decision that was genuinely discussed and settled but never made it into memory or `.dev/docs`; a live-capture-only design misses exactly the backlog that predates it. Needs shaping: what counts as "a decision worth backfilling" versus ordinary discussion noise (the same non-obvious-decision judgment already used for live capture, applied retroactively, is one candidate); what triggers a pass (on-demand only, the same shape as "the ultimate question," versus a periodic sweep); and how to avoid it becoming a low-value audit run once and never repeated, the same risk already flagged below for `testing/fixtures.md` and `cold-read-review.md`.
- **Are `testing/fixtures.md` and `cold-read-review.md` actually being run, or built once and left dormant?** Every convention fix this week came from a real, live incident; agentics' testing practice is entirely reactive so far. These two exist specifically for *proactive* red-teaming (a fresh agent trying agentics cold before a real incident teaches us the same gap the hard way), but nothing has confirmed they've actually been exercised since being written. Worth checking before assuming they're pulling their weight, not necessarily building anything new
- **Proactive scope/effort estimation before large tasks, with incremental checkpointing as the default execution shape.** When a task is large enough to risk running out mid-way (Claude Code's own usage limits are the motivating case, though the underlying risk, interruption before completion, isn't specific to that one mechanism: a crash, a context limit, a session simply ending), an agent should be able to say so before starting, and help break the work into a sequence of individually-valid checkpoints rather than one large, uninterruptible push. Not designed yet: how an agent would actually estimate this risk in advance (scope size, file/repo count, and the session's own accumulated history so far are plausible signals, nothing concrete yet); what a "checkpoint" concretely means as a deliverable shape (self-contained and committable seems right, matching the existing "collapse iteration to outcome" discipline, but applied during planning, before work starts, not just to session-log hygiene afterward); and whether this becomes its own convention or folds into existing ones (`Checking in before non-trivial decisions`, `Scope discipline`). Generalize past the Claude-specific "usage limit" framing to the underlying property, interruption risk in general: the same "state the property, not the instance" lesson `property-scoping-recurs` already named
- **"Is everything I know actually written down?": a proactive completeness check for intra-project knowledge, not just cross-project.** A distinct but related idea to the cross-pollination item below: that one is inter-repo (Arranger informing Stage); this one is about different agent sessions working on *different features of the same project* staying mutually aware of decisions and patterns established in a conversation the other never saw, not the code changes themselves, the insight behind them. `.dev/docs` already exists for exactly this, but agents only write to it on demand, not proactively. Demonstrated directly (2026-07-30): asked an Arranger agent "is all the knowledge you hold here documented somewhere, either in project memory or actual files in repo?" It correctly separated durable facts (project memory as compact pointers, `.dev/docs` holding the real substance, e.g. a memory entry that's one line pointing at a full write-up) from what's correctly *not* preserved (the diagnostic reasoning chain itself, by design, matching "collapse iteration to outcome"), and caught something real and at-risk: a PR review draft sitting in a session scratchpad with nowhere durable to land unless posted or saved.

  **Design resolved in discussion (2026-07-30), not yet written into a convention:**
  - **Two tiers, not one.** A "lesson learned" (a decision with a non-obvious why, a pattern not derivable from code, a cross-cutting constraint) writes automatically, live, at the decision point, not batched. Everything smaller stays in project memory by default, promoted only on explicit request or once enough of it accumulates into something actionable.
  - **The "worth documenting" test:** would a *different* session, working on a different part of the same project (or a project this one visibly affects), need this to avoid re-deriving it the hard way or contradicting a decision already made? Deliberately narrow: excludes most of what a session accumulates (dead ends, exact commands tried, the reasoning chain itself), the same "collapse iteration to outcome" instinct `session-discipline.md` already applies to session-log prose, generalized here to knowledge as a whole. What clears it: a decision with a non-obvious why; a pattern or constraint not derivable from reading the code cold; a fact about an external dependency nothing else documents. What doesn't: anything reconstructable from the current code, and the investigative path itself once the answer is known.
  - **Memory or `.dev/docs`, and which project:** pointer vs. substance, not a competing choice, same as above. Memory stays a short pointer; if the real explanation runs longer than a few sentences, that substance belongs in `.dev/docs`. When the current project has an already-known relationship to a dependent one (`~/.claude/projects.md`'s existing "Cross-project" field, no new relationship-tracking needed), a lesson with a visible side effect there writes to that project too, not just this one.
  - **Trigger is per-decision, not a session-end sweep**, so a concurrent or later agent can pick up a side effect without waiting; a live "should I document this now" circuit at each decision point, reusing the same non-obvious-decision judgment already required for session-log bullets and tech-debt entries, just applied one moment earlier and routed to a durable location instead of only the day's session file.
  - **Folds into "Definition of done" above** as a sharpened criterion (not done until lessons learned are persisted where they belong), enforced by the existing "Refinement passes" checkpoints rather than a separate new mechanism.
  - **Universal**, not project- or product-family-specific: `.dev/docs` and memory hygiene are already universal template mechanisms.

  Still open: the actual convention prose and where exactly it lives (a `session-discipline.md` addition, most likely, given the "Refinement passes" tie-in); whether it's the same underlying mechanism as "the ultimate question" or a distinct trigger worth naming on its own
- **Cross-pollination of expertise: a specialized agent proactively informing another project's devctx.** Demonstrated directly (2026-07-30): asked the Arranger agent, which has deep context on `arranger-components`/`sqon`, to write up what Stage actually imports from those packages (verified against Stage's real explorer-page code, not generic docs) as a new `.dev/docs/arranger/README.md` inside Stage, then add a narrow dispatch line to Stage's `AGENTS.md` ("Working on Arranger integration -> read `.dev/docs/arranger/README.md`") specific enough to actually fire, rather than relying on Stage's existing generic "Deploying or debugging a service" trigger. It surfaced one concrete, actionable finding along the way (`explorer/index.tsx` still using the deprecated `hasValidConfig` query Arranger's own migration guide says to replace), and explicitly left alone everything a separate concurrent thread in Stage already had in flight, a real, working instance of the scope discipline this needs. Not yet designed: this as a *named*, repeatable pattern rather than an ad hoc instruction; whether it's one-directional (Arranger -> Stage) or genuinely reciprocal (multiple specialized agents keeping each other current on their own areas, not just one informing another once); how staleness gets handled once the source project's real implementation moves on from what got snapshotted; and whether this is agentics' concern at all (a convention describing the pattern) versus the "agent manager" item above (the orchestration mechanism that would actually run it)
- **Should a live-pointer read from a different project resolve to `HEAD`, not the raw working tree?** Found while investigating a contributor's agent writing directly into this repo: a live pointer currently resolves to whatever's actually sitting on disk at the recorded clone path, uncommitted drafts included, no gating on commit state at all. `rewrite-freely-until-committed` already treats uncommitted content as a draft everywhere else in this repo's own conventions; a different project's live-pointer read is the one place that draft state currently leaks out as if it were settled. The principled fix: an *other* project's live-pointer read resolves to last-committed content (`git show HEAD:template/conventions/<file>.md`, or the GitHub URL, both already "last pushed" states), while a session actually working inside agentics itself keeps reading the working tree directly, since drafting in place is the point there. Not yet decided: this adds real mechanism complexity (an adopting-project agent needs to know to read via `HEAD`, not a plain file read) for a risk that's so far proven exactly once (today), not a recurring pattern; worth confirming it's worth the cost before implementing, not something to build unprompted
