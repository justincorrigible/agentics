## Phase 3: personal context portability

Goal: a user can maintain a private GitHub repo mirroring their `~/.claude/` global setup (CLAUDE.md customizations + global memories), so that switching to a new Claude account doesn't erase accumulated rapport and preferences.

Design sketch:
- User creates a private repo (e.g. `<user>/claude-context`) following a structure agentics defines
- Suggested structure: `CLAUDE.md` (global instructions snapshot), `memory/MEMORY.md` + memory files, optionally `projects/<project>/memory/` for project-specific memories
- agentics provides: template for the private repo structure, a standard bootstrap prompt the user gives a fresh agent to reconstitute context from the private repo, guidance on what belongs there (preferences, feedback patterns, working style) and what does not (credentials, project-specific ephemera, anything derivable from code)
- Sync discipline: end-of-session or on-demand; the user commits manually: no automated push

Open questions:
- Should agentics include a `template/personal-context/` scaffold, or document the pattern only in prose?
- How does the bootstrap prompt discover which projects to also load memories for?
- Where does the private repo live relative to agentics in the contribution/update-propagation model?

## Design questions: needs more thinking

- **Startup instruction-file integrity check:** at session start, run `git log --oneline -- CLAUDE.md AGENTS.md` and flag unexpected changes not made by the repo's lead developer; useful tamper signal but adds a mechanical step: decide whether this is a hard rule, optional guidance, or a softeng-specific convention
- **Context sync across projects:** the upstream-update check (`upstream-check.md`) now surfaces drift automatically for opted-in projects, but the "source of truth" ownership model is still informal: which conventions are global, which are template, which are project-specific, and how to reason about overlap when a project has genuinely diverged on purpose

- **Integration with existing agent setups:** the current approach (initialization question + "supplementary" flag) is minimal; deeper questions remain: should the agent offer to review existing conventions for conflicts? How prescriptive should softeng conventions be when a rich setup is already in place? Is "supplement on conflict" even the right default, or should users choose a merge strategy?
- **No destructive-action gate for the role that can actually act destructively.** Verified 2026-08-17: "irreversible" appears exactly once in the whole template, in `AGENTS.roles/general.md` (the non-technical role), covering sending an email and deleting a file. `AGENTS.roles/dev.md` is five lines and states it "adds nothing." Critical constraints say nothing about destructive commands, and `AGENTS.md`'s hard-to-reverse-footprint rule reaches the developer's own machine state, not a cluster or a database. The only infrastructure guard, `AGENTS.softeng.md`'s Jenkins rule, covers Terraform. Nothing covers `kubectl delete`, `helm uninstall`, a migration against a shared dev database, dropping an OpenSearch index, `git push --force`, or `git reset --hard`, all daily-available in this team's repos. The gap is a placement inversion rather than a missing idea: the rule exists, aimed at the role least likely to hold a kubeconfig. Belongs in Critical constraints as a universal rule. No specific incident in the record yet, so the open question is how strong to make it without turning routine infrastructure work into a confirmation prompt every few commands.
- **Debugging has no convention and no dispatch trigger.** The only debugging line in the dispatch table is a conditional pointer at `.dev/docs/<service>/`. Three real debugging lessons already exist and are each filed where a debugging session never loads them: check live runtime configuration before theorizing about code paths, and reproduce the suspect state rather than reconstructing it from a diff or reflog (both in `review-conduct.md`, dispatched by PR review), and check for a working sibling instance before diagnosing from first principles (in `code-style.md`, dispatched by writing code). A session whose whole task is "this is broken" reviews no PR and writes no new code, so it loads neither. Those three sections are most of a `conventions/debugging.md` already; what needs deciding is whether to create the file or widen the existing dispatch triggers, and whether a general stopping rule (three approaches failed, going in circles, the request rests on a false premise) belongs there or in Interaction parameters, since the one recorded instance of that, several rounds of wrong theories ending only when the developer asked for a test to be run, shipped as a debugging heuristic rather than as a rule about noticing the loop.
- **"Say it is unknown rather than produce a plausible value" has been fixed three times narrowly and never stated generally.** Zero files in the repo contain the words hallucination or fabrication. The three narrow fixes: `session-timestamp-no-time-source` (an agent padded a timestamp rather than fetching the time, then a second agent "corrected" it to a different fabricated time, which the CHANGELOG itself calls the same guessing anti-pattern in a new disguise); `agent-index.md`'s rule against falling back on whichever name looks plausible; and `review-conduct.md`'s state-what-was-checked rule, scoped to review reporting only. `AGENTS.roles/ai-eng.md` covers this for AI systems the developer builds, not for the agent reading the file. This is the exact shape `property-scoping-recurs` exists to catch, and the generalization never happened. Belongs in Interaction parameters as a stance.
- **Nothing in the framework is addressed to the human. Security half shipped; the rest is open.** Every lesson learned ships as an agent-side rule with no developer-side counterpart. `template/AGENTS.md` states the position outright, and `template/README.md` and `DEVELOPMENT.md` are mechanics. `docs/security-for-developers.md` (2026-08-17) now covers the security slice: what to verify rather than take on the agent's report, which agent claims are unreliable and why, the trust boundaries only a person can hold, and recovery once something has gone wrong. It also proved the general point, both security documents had been unreachable from either README, so a human-facing file existing is not the same as anyone finding it. Still open, and deliberately not folded into that file since it is a different subject: what a good instruction looks like, how to correct a wrong assumption so it actually holds rather than resurfacing next session, when to distrust agent output in the ordinary non-security case, and how to onboard a teammate onto an agentic project. Distinct from the contributor-bootstrap item (onboarding someone into contributing to agentics) and from the dev-versus-non-dev item (which conventions load). Candidate shape: `docs/working-with-your-agent.md`, with the security file as the model for register and for being linked from somewhere a person actually reads.
- **No convention for backing out of a mess the agent made.** Nothing covers a half-applied multi-file edit, a file left syntactically broken, a bad commit already made, or a session that needs unwinding. The only recovery-shaped content, `session-discipline.md` § Unattributed working-tree changes, is about another session's changes and leaves keep-or-revert to the developer. The checkpointing item above is about preventing interruption damage, not recovering from it. Evidenced twice in this repo's own record: a hand-edit that broke a file's JSON validity with recovery improvised, and a session where the developer reverted an agent's changes themselves. Belongs in `session-discipline.md`, which already owns git.
- **Two smaller uncovered task types.** Dependency *upgrades*: `code-style.md` covers introducing a dependency thoroughly and stops, leaving bumping an existing one (read the target's changelog for breaking changes first, one at a time versus batched, a transitive bump that breaks the build, a Dependabot PR handed to an agent) uncovered, across roughly twenty repos running Dependabot; note the naming collision that will mislead anyone searching, since `upgrading-adoption.md` is about agentics' own version. Safe *removal*: nothing covers finding consumers before deleting an exported symbol, whether to deprecate first and for how long, or a last caller living in another repo, which matters here because Overture packages cross repo boundaries with no local signal; the already-recorded case of Stage still calling a deprecated Arranger query is filed as cross-pollination rather than as this gap. Both speculative-to-weakly-evidenced, so neither clears "prove it before templating it" on its own yet.
- **Resolved: `id` stays whole, `window` is the container's name, and there is no prefix field.** Two corrections in one day landed here, both from the developer. The first: a first-listed folder's basename is an artifact of workspace ordering rather than a name for anything, so requiring `window` to equal it was backwards. The response to that was itself the second mistake, splitting the handle and storing the prefix as the durable half, on a measurement that zero of fifteen handles survived a rotation while four of four prefixes did. The developer questioned whether that split bought anything, and it does not: the measurement counted cardinality and reported it as durability, and a prefix is a substring of the handle regardless, so a dead `id` already yields one for free and a separate field can never know something `id` does not. Checked live rather than argued: matching seven recorded ids against a listing separated two current from five dead with nothing sent, while the prefix fallback for one of the dead offered six candidates that this convention's own rule against guessing forbids choosing from. Each value now has one job. `label` is identity and developer-assigned, `window` is the container's name and developer-meaningful, `id` is the full handle checked against the live listing before use. The lasting gain from the detour is smaller than either wrong turn and sits elsewhere: a stored `id` is verifiable for free before sending, which the convention had explicitly denied was possible.
- **Does `id` earn its upkeep? First real test says the objection was stronger than the answer given to it.** `id` shipped in 0.16.0 over a considered objection from the `Arranger` session: a handle is valid only for its session's lifetime, so a stored one is confidently wrong the moment that session ends. The answer given was that a stale `id` costs one failed send and a correction, the same price as never having had one, while a live one skips the narrowing. Both halves of that held up overnight and it still came out badly. All eight ids collected on 2026-08-19, each confirmed by its holder rather than guessed, were stale within about twelve hours: every session had restarted, and `ListAgents` showed eight entirely new handles. The send failed cleanly and named alternatives, so the failure mode is safe as designed, and `window` narrowing still worked because it is derived rather than stored. What did not hold is the value: the effort to collect eight confirmed ids bought roughly one working day, and the refresh-at-session-start rule cannot recover it, because a new session cannot observe its own handle, so a mass restart leaves every session simultaneously unable to refresh and needing a peer handshake each. Rebuilding a directory that was complete an hour earlier costs N exchanges, while the `window` fallback costs nothing and survives restarts untouched. **Partly answered the same day, by the developer, with the session-start sibling handshake.** One exchange at session start, telling a sibling the handle you addressed it by and asking for yours, refreshes two entries at once, because each side holds exactly the fact the other cannot observe. That is the "something that makes reconstitution cheap" this item was asking for: recovery becomes one message per session, taken as a side effect of starting work, rather than a directory-wide peer-diff scramble. Still open, and narrower now: whether one handshake per session start is enough coverage in practice, or whether a directory of N entries needs more than N/2 exchanges to come back reliably; and whether the staleness re-check, reframed as comparing `date -u` against the entry's own `updated` rather than as an undetectable "after silence" trigger, actually fires often enough to matter. Do not resolve either from the design's own reasoning; it predicted the staleness correctly and still misjudged the cost. **The cost half is now answered, on 2026-08-20, and in the field's favour.** "A stale `id` costs one failed send" was itself wrong: a stored handle is checkable against the live listing for free, in the same call that any fallback would need anyway, so a dead one costs nothing and is never sent to. That removes the downside entirely and leaves only the upkeep question above, which is about what collecting ids costs rather than what carrying stale ones does.
- **The window is not a safe anchor for identity or for memory, and every mechanism built on it inherits that.** Established across three separate findings rather than argued: a runtime handle's prefix comes from the workspace's first-listed folder, so it names a window and never a project; a family keyed on window is exact for one product family here and wrong for another, because two workspaces share a first folder; and project memory is keyed by the same resolved path, so every session in a window loads the same memory whatever it is working on. The third was found the hard way: a session opened to review an unrelated proposal document loaded this repo's memory and surfaced another conversation's pending work as though it were its own. The developer's framing is that a window's main agent should be isolated deliberately rather than defined by an accident of folder ordering, and that generalizes past identity: anything scoped to "this window" is scoped to a path-encoding artifact. **Mostly resolved, and the framing above was wrong.** The stated blocker was that an anchor must be observable from inside the session and `label` cannot be self-derived. It cannot, and it does not need to be: the developer pointed out that a label is established by proposing one and having them approve or change it, which is already the documented registration flow verbatim, propose from visible context and get a confirmation before committing. So `label` is the anchor, and combined with the session-start sibling handshake for `id`, a fresh session establishes both halves of its identity at start with no dependence on `window` at all: the durable half from the developer, the ephemeral half from a peer, each from the only party that can supply it. What remains genuinely unfixable here is narrower: memory placement is keyed by resolved path by the harness rather than by anything agentics controls, so a window's sessions will keep sharing one memory directory whatever the index says. That is worked around rather than solved, by the rule that memory holds durable facts and never instructions addressed to whoever reads next. Still open, and small: whether `window` should be demoted in the resolution ladder now that three findings have gone against it as an identity signal, or left as what it actually is, a cheap derived filter that is correct for narrowing and wrong for anchoring.

  **Third undermining, and this one is decisive enough to put the field itself back on the table.** An adopting session reported that its handle rotated while the session never restarted, and a sweep of the live listing found every recorded `id` dead, eight of eight, including this repo's own, which had been edited hours earlier on the assumption it was live. So rotation is independent of session lifetime and unobservable from inside the session it happens to, which means the session-start refresh added to rescue the field cannot cover the case that most needs it. Verify-on-contact has been added and is the right shape, since it fires when accuracy matters rather than when it is convenient, but it only helps sessions that are in contact. The honest tally over the field's two-day life is that it has been stale more often than correct, and each fix has addressed the symptom the previous one exposed rather than the premise. The original objection, that a stored handle is confidently wrong the moment it changes and carries no signal, has now survived three attempts to answer it. Worth deciding rather than patching again: keep `id` as a within-session convenience exchanged in messages and never persisted, which is what was argued before it shipped, or keep the field and accept that its correctness is measured in hours. Do not decide this from the design's own reasoning, which has now been wrong about the failure mode three times.
- **Family heads: a per-family triage point for unclaimed components.** Developer-originated, designed with the `iMicroSeq Portal UI` session on 2026-08-19 and confirmed directly. Full design, including the four resolved questions and what is still open, in `.dev/docs/atlas/family-heads-design.md`. Not shipped as a convention: no head has operated yet, so it fails this repo's own prove-it-before-templating-it bar. The finding most likely to reshape it, and the reason it is worth reading before implementing: the family is the product family, not the `window`. Tested against the live index, `iMicroSeq`'s window is exactly its family while `softeng`'s holds a tool plus three unrelated Overture components, because two workspaces share a first folder. A head keyed on window would ship the missing product-family concept into a new mechanism instead of closing it, which makes this and the product-family addendum item the same gap.
- **Two sessions legitimately working the same project have no way to label themselves usefully.** `agent-index.md` says labels are descriptors rather than identifiers, so a collision is permitted, and tells a registering session to negotiate with the existing holder before taking a name already in use. It does not say what a negotiated outcome should look like. Confirmed 2026-08-19 by a session that hit it and correctly declined to guess: it works in agentics itself, would match the `agentics` label, and that label was already held by another live session in the same window. Two entries both reading `agentics` would be worse than one, since a lookup returning both tells a caller nothing about which to address, and the `id` field does not help because the caller does not know which session it wants yet. Likely shape is a qualifier naming what each session actually owns rather than the project they share, `agentics (conventions)` versus `agentics (release)`, but that needs deciding rather than inventing: `label` is developer-assigned by design, so any convention here has to describe what to propose, not impose a format. Related and worth resolving together: nothing says whether a Member entry should be removed when its session ends, which is why `Lyric and Maestro` currently sits registered with no live session anywhere, a state that is correct under the current rules and indistinguishable from a stale entry.
- **Is the convention set drifting toward one project's failure modes?** Raised unprompted by an adopting project's own agent, about itself, which is the least self-serving direction the question could come from: if most recent lessons originate in one repo, the conventions may be tracking where the agent-hours happen to be landing rather than genuinely broad gaps. Checked rather than accepted, and the check is weak in a way worth stating: entries are deliberately anonymized ("an adopting project's agent"), so grep gives a floor on any one project's share, not a measurement. That floor across the last three releases is 1 of 29 entries naming Arranger in 0.15.0, 0 of 8 in 0.14.0, 2 of 25 in 0.13.0, with a further 2, 0, and 3 naming an unattributable adopter. So the raw claim of three consecutive releases dominated by one project is not supported by what can actually be counted, but the underlying concern is not answered by that either, since the anonymization that protects contributors is exactly what makes the question unanswerable by grep. **A private tally was proposed and checked, and it is the wrong fix, because the data already exists.** `.dev/sessions/` is committed (33 tracked files) and names source projects freely: Arranger appears in 16, Stage in 9, helm-charts in 6, Lyric, Maestro and Usher in 4 each. So the anonymization is a `CHANGELOG`-only courtesy in the distributed artifact, not a secrecy requirement, and provenance is already public. Recording it a second time in project memory would duplicate a fact already written down, which is what this repo's own single-source rule exists to prevent, and the copy would drift. It would also under-count silently: memory is per-agent and per-machine, so a tally kept by one contributor never sees what another ships, while still reading as a complete census, the same scoped-measurement-reported-as-unscoped shape as `scoped-search-unscoped-claim`.

**The real gap is smaller: nothing links a `CHANGELOG` slug to the session that produced it.** Both artifacts already exist and both are already committed; a session-log grep gives a noisy corpus (a project named in a log is not necessarily the source of that entry's lesson) only because the connection is missing. Naming the slug in the session entry that produced it would make provenance exactly queryable at no storage cost, with no new file, no memory entry, and no change to what the released `CHANGELOG` says. Worth confirming it stays cheap in practice before it becomes a rule.

**Two different questions, and neither is answered by counting.** A tally, however sourced, measures who is loudest. Arranger's actual concern was whether the conventions track where agent-hours happen to land, which is a question about the projects generating *no* entries, and those are invisible to any count of entries. That half needs deliberate sampling from quiet projects, on the reasoning that a project producing no lessons is more likely under-observed than problem-free. Same root as the dormancy question already open for `testing/fixtures.md` and `cold-read-review.md`: agentics currently only learns from what happens to report itself.
- **Growth has no bound and nothing measures it. Two of the named fixes are done; the budget is not.** Measured 2026-08-17 at about 111,000 bytes for the mandated session-start read. Since then: `upstream-check.md` was split out of `convention-levels.md`, and `session-discipline.md` was split by trigger into `entry-formats.md` and `agent-troubleshooting.md`, taking it from 61,628 to 40,402 bytes. The session-start read now stands at 88,211, down 10.3% from the 0.15.0 baseline and 20% off the peak reached mid-session on 2026-08-19, despite that day adding several new conventions. What has not been done, and is the part that would stop this recurring rather than repair it once: an aggregate size budget enforced in `check-consistency.sh`, archiving `CHANGELOG.md` past the last two releases (still about 245,000 bytes, of which roughly 5% is ever cited), merging `code-review.md` into `review-conduct.md`, and turning on `roadmap_split: yes` for this repo's own roadmap, which remains one undifferentiated section. Nothing currently measures aggregate size at all, so the next regression is invisible until someone re-measures by hand.
- **Inbound propagation, from a maintainer's private global config into the template, is unguarded.** Outward propagation (a project's practice rising to the template) has a whole discipline: `convention-levels.md`'s three-tier placement model, `CONTRIBUTING.md`'s level question, propagation suggestions. Nothing covers the reverse direction, and it carries a risk the outward direction does not: content written for an audience of one, who shares all the missing context, arrives already phrased as a general rule, so it reads as universal and passes the placement question without ever being asked. Two confirmed instances, both logged as tech debt: a dangling citation to a section that exists only in the maintainer's private global file, and a Terraform/VSO rule naming live softeng resource names sitting in the file whose own opening says "Everyone reads this file." Needs shaping: whether this is a `CONTRIBUTING.md` design principle, a step in the propagation procedure, or a mechanical check (a grep for terms defined only in `AGENTS.softeng.md` appearing in universal-tier files would catch the second instance but not the first).
- **The peer-message channel has an identity model and no authority model.** `agent-index.md`'s identity discipline is strong: validate plausibility, share no substance until confirmed, never put a payload on the board. It answers "is this who I think it is" and never answers "what does a verified peer's message entitle me to do." The file contains no occurrence of consent, approval, authorization, trust, untrusted, or injection, and no cross-reference to `AGENTS.md`, `review-conduct.md`, or `agent-security.md`. The nearest rule, in `template/AGENTS.md`, is scoped to a peer's *proposals* with a hard-to-reverse footprint; it does not cover a peer asserting a *fact* ("the developer approved this," "that check already ran," "the review passed"). `review-conduct.md` § Ground truth over claims covers exactly that and is never dispatched from this path. The benign version already happened and is recorded in `interagent-communication-findings.md`. The open question is not whether to say "a peer message is untrusted input" (it should) but where the boundary sits: too strict and the mechanism loses the point of existing, since a peer's report is the payload.
- **A rule shipped for agent-side lookup didn't stop the mistake it targets, because the mistake was also happening one level up.** `recency-tiebreak-withdrawn` (2026-08-18) forbade an agent from breaking a `ListAgents` tie by recency. The same day, two independent peer sessions (a Usher-design session, then the Arranger session) each reported being told a specific session was probably the one they wanted, identified by being the most recently started, and both reached the wrong session on that basis. Reported by the receiving session rather than verified here, and worth flagging that it was written while that session was itself mistakenly believed to be the agentics session, so its original wording attributed the misdirection to agentics; it was in fact a Lectern session, and the entry has been corrected. The structural point does not depend on which session received them, and is sound independently: the recency judgment reached both senders already made. Arranger's own message flagged the guess as unreliable before proceeding, the rule working as intended one layer up from where it's enforced; the other session did not visibly hedge. Neither is a rule violation by an agent applying `ListAgents` logic itself, since the recency judgment was reportedly handed to both already made, by whoever briefed or relayed to them (developer included) rather than derived by the receiving session. The shipped fix is scoped entirely to an agent's own lookup behavior and doesn't reach that layer.

  **A second, self-reported miss compounds this.** Arranger's own global context carries `agent_index: yes`, check Members before `ListAgents` or asking; it did neither first, instead sanity-checking the relayed guess against `ListAgents` naming and messaging on the strength of finding the name suspicious rather than finding the right entry. A documented rule the session was already supposed to follow didn't fire until asked to reconsider, the same recurring "a rule existed and did not fire" shape as several entries above.

  **A third, deeper gap surfaced once the lookup was actually done correctly, and the developer's own read corrected the diagnosis again.** All three sessions in this exchange concluded no live session matches `iMicroSeq/submission-service`; that conclusion was itself the mistake, one level past the first two. `ListAgents` carries three `virusseq-portal-*` handles; `virusseq-portal` is `iMicroSeq`'s pre-rebrand product name, still the literal folder these sessions run in, and the sessions there self-identify as iMicroSeq's agents, matching the Members registry's own `iMicroSeq Portal UI` entry (`project: iMicroSeq/virusseq-portal`, `window: iMicroSeq`) exactly. The target session is very likely live, present in the same `ListAgents` output all three parties already had, and invisible to a project-name match only because its runtime handle carries a retired product name the Members record itself has already moved past. The `iMicroSeq Portal UI` entry proves this isn't guesswork: it declares `window: iMicroSeq`, and `ListAgents` still shows `virusseq-portal-*` regardless, meaning the handle is derived purely from resolved `cwd` and never consults a session's own declared identity fields at all. `agent-index.md`'s existing "handle prefix is weak corroboration, not identification" framing undersells this: a stale or rebranded folder name doesn't just weaken corroboration, it can point away from the correct entry entirely while reading as a clean non-match, exactly what happened here across three separate sessions. Two separable fixes worth keeping distinct: renaming the actual workspace/folder so the handle stops carrying a retired product name (local to that one project, and likely to recur for any other renamed or rebranded one); and a documented step here for reconciling a Member's declared `project`/`window` against a live handle that doesn't textually match it, since prefix mismatch was read as absence by three sessions in a row rather than prompting a closer look.

  Also noted in passing, not yet investigated: that Member entry's `updated: 2026-08-19T01:20` is timestamped after the current date in the sessions that read it (2026-08-18), worth a look since staleness logic depends on the field being accurate; a clock or timezone difference is the likely cause. Full text of all three cross-session messages is available from the agentics session that received them if useful for diagnosis.
- **Review depth and method have no convention.** `review-conduct.md` covers stance, disposition per finding, ground truth over claims, and the structural-pattern sweep. Nothing covers how thorough a review should be or what makes one complete, so nothing distinguishes "I read it all" from "I searched it several ways." Direct evidence, same repo and same day: a deliberate full read of every file found four items; a multi-lens pass hours later, with nothing changed in between except method, found substantially more in the same files, including one defect that a reading pass structurally could not have caught because the file reads correctly and only executing it reveals the fault. Needs shaping: what triggers the deeper form (not every review warrants six lenses), whether the lenses are a fixed list or chosen per target, and how this relates to `testing/cold-read-review.md`, which is the same instinct aimed at a different target. Reasoning: `.dev/docs/atlas/multi-lens-review-2026-08-17.md` § Method.
- **`deterministic-by-design.md`'s mechanically-enforceable bucket: two of four gaps now closed, two open.** Closed 2026-08-19: the dashes check now covers all four banned forms rather than the two the old grep tested, and schema drift between a convention and its bootstrap copy is checked mechanically after shipping three times unnoticed. Still open, both named with their specific mechanism: the AI-attribution check runs from `pre-commit`, where the commit message being written does not yet exist, so it is gated one commit late and belongs in `commit-msg`; and "draft, never post" has no enforcement at all despite being the most irreversible action in the repo, where a `PreToolUse` matcher on `gh pr comment`/`gh pr review` would force the draft path structurally. A third, softer: the agent-neutrality check prints eighteen lines every run and can never fail, which is alarm fatigue by construction and needs the framing filter that would let it fail honestly. The file's own "fully converted" claim stays wrong until at least the first two land.
