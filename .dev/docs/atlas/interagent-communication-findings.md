# Interagent communication: findings so far

Empirical findings from live-testing Claude Code's cross-session messaging (`ListAgents`/`SendMessage`) on 2026-08-08: real peers, real sends, both receiving and sending. Gathered as prep material for whenever agentics defines an actual "interagent communication" convention, not a design itself. Two findings from this same investigation already became real convention changes and aren't repeated here in full: the unsaved-buffer troubleshooting entry in `session-discipline.md`, and the "delivery isn't action" extension to `review-conduct.md` § Ground truth over claims.

**Every finding below is Claude-Code-specific and must not be taken for granted when this becomes a real convention.** This is empirical data about one agent's tooling, not a cross-agent design. Two distinct risks, not one: (1) a different agent type may have no equivalent capability at all, not just a platform restriction within Claude Code itself (already noted separately in `.dev/roadmap.md` § "Agent manager": not on Windows, Bedrock, GCP Agent Platform, or Microsoft Foundry); (2) an agent type that does have some form of cross-session messaging may not share any of the specific behaviors documented here (the `[ref]`-requirement, delivery-vs-action semantics, sub-agent unreachability, the on-disk registry mechanics), so none of it generalizes by default. Whatever convention eventually gets written from this must (a) check for the capability rather than assume it (the same "verify before assuming a limitation" instinct this developer already applies to Claude Code's own tooling), (b) frame it strictly as an optional accelerant, not a dependency, since devctx/memory already covers the general case with no session needing to be concurrently running, and (c) follow the same `(for Claude: X; for other agents: Y)` framing used everywhere else in the template, not a Claude-Code-only default.

## Terminology: "session" is the container, "agent" is who's in it

Claude Code's own tooling names things three different ways depending which layer you look at: the command itself is called `ListAgents` (implying it lists agents), its own output text labels the result "Peer sessions" (implying sessions), and a rejected `SendMessage` call returns "'X' is not an agent in this conversation" (agent again). The resolving mental model: a session is the container, the chat window or background process; the agent is who's actually in it, the thing you talk to. A session's main agent can locally spawn sub-agents (via the Agent/Task tool), which live and die within that session, never independently reachable (see below). `ListAgents` is really listing reachable *agents*, correctly, it's just that the only agents reachable across sessions happen to be each session's main one, so in practice its results are one-per-session and read like a session list. Whenever agentics writes an actual convention about this, keep the distinction explicit: "session" for the container, "agent" for who's in it, "sub-agent" for something spawned locally within one.

## The on-disk registry

Each session self-registers in two places:

- `~/.claude/sessions/<pid>.json`: one file per session, containing `pid`, `sessionId`, `cwd`, `startedAt`/`procStart`, `version`, `peerProtocol`, `kind`, `entrypoint`, `messagingSocketPath`, and a `name` (with `nameSource: "derived"` when auto-generated from the folder name, e.g. `myapp-3f`).
- `/tmp/cc-socks/<pid>.sock`: the actual bound inbox socket a peer delivers to.

**Visibility in `ListAgents` requires both, registration alone is not enough.** Confirmed directly by diffing the two sets: several sessions had a `.json` registration file but no matching socket, and none of those appeared in any `ListAgents` call, regardless of whether the underlying process was alive. One clean case: two sessions on an older Claude Code version (pre-v2.1.224, before the feature's version requirement) registered but never bound a socket. One unresolved case: two sessions in the exact same project directory, same version, same `peerProtocol`, started about 90 seconds apart, only the second had a bound socket. Consistent with a "reset by switching a multi-root workspace's first-listed folder" pattern superseding an earlier session in the same window, but not confirmed from the files alone.

**The registry file's `name` field is stale after a `/rename`.** It's captured once, at registration, and never updated. A session renamed mid-conversation (confirmed directly: one session's live display name changed to something project-specific, unrelated to its derived name) still shows its original derived name in `~/.claude/sessions/<pid>.json`. The reliable cross-reference when names disagree is the socket path: an incoming message's `from="uds:/tmp/cc-socks/<pid>.sock"` matches exactly one registry file's `messagingSocketPath`, regardless of what name either side is currently displaying.

**No separate window or workspace identifier exists.** The registry gives `pid` and `cwd`, nothing naming which of several open windows a session belongs to beyond the project path itself.

**No message-log file exists anywhere in `~/.claude`.** Checked `history.jsonl` (general prompt history, unrelated fields, no cross-session-message content) and `file-history` (per-session file-edit snapshots, unrelated). There is no way, from files on this machine, to see what else a peer session has sent or received; that information, if visible at all, only exists inside that peer's own private conversation.

## `SendMessage` requires a just-observed ref, not only for duplicates

A real four-way send test (four distinct, non-colliding names) had every single bare-name send rejected with "not an agent in this conversation, re-send with the ref to confirm you mean: X [ref]." Retrying with the exact ref from that same rejection succeeded every time. The tool's own top-line description suggests the `[ref]` suffix is only needed to disambiguate a collision; the real behavior observed is stricter: a cross-session peer's ref must come from something just observed in this same conversation (a `ListAgents` listing or a rejection error) before the first send to it succeeds, functioning as a "you didn't just guess this identifier" check, uniform across every peer tested, not a per-session quirk.

## No "main" session per window; every thread is an independent, peer-equal registration

A single window, or a single project, can have many separate conversation threads open at once, each one that has cross-session messaging enabled registers its own `pid`, its own socket, and its own derived name, fully independently. Confirmed directly: six separate registrations existed for the same `overture/arranger` directory at once, all showing as distinct, equally-reachable peers in `ListAgents`, nothing in the registry marks any one of them as primary or authoritative for that project. There is no "main" session to route through; addressing a specific thread means addressing its own specific name or ref, and a sibling thread in the same window is exactly as reachable, or unreachable, as one in a completely different window.

**The derived name reflects a resolved `cwd`, not necessarily what the thread is actually about.** This connects directly to the multi-root workspace quirk `session-discipline.md` already documents elsewhere (a multi-root workspace resolves to whichever folder is listed first, regardless of which file is actually open): if two conversation threads share a multi-root workspace, both could derive the same project name from that same first-listed folder even while the human is actually discussing something else entirely in one of them. Don't assume a session's `ListAgents` name confirms what it's actually working on, only which directory it resolved to at registration.

**Delivery reliability is genuinely mixed, not resolved either way.** The first `agentics-8b` silence turned out to have a good alternative explanation (renamed to "Lyric and Maestro," likely just a different tab or focus than what was being watched), and a retry to it, plus a fresh send to a brand-new session (`virusseq-portal-5b`), both came back clean and immediate. But a separate pair of replies sent to `arranger-56` ("Search Server - multicatalogue") showed no observable effect, with no rename to explain it away this time. Leading hypothesis, not yet confirmed: a client-side glitch (the VSCode extension itself) affecting specific windows or sessions, rather than the underlying messaging channel being inherently unreliable, the same "verify before assuming a limitation" instinct that resolved the earlier extension-version issue, not yet resolved here. Don't conclude either "it's reliable" or "it's broken" from this; the honest state is mixed, session-specific, and still open.

**`cwd` can be a complete mismatch for what a session actually knows or is doing, not just an imprecise signal.** `agentics-8b`/"Lyric and Maestro" registered `cwd: .../softeng/agentics`, yet that session is entirely about Lyric and Maestro, two completely different projects, neither of which is agentics. This isn't a partial or approximate mismatch, it's total: nothing about the registered `cwd` reflects what the session is actually for. Relying on `ListAgents`' derived name or `cwd` to infer a peer's expertise or current focus is not just imprecise, it can be entirely wrong.

**What we've been calling "project memory" is really workspace memory, and that has a real consequence, not just a naming one.** `cwd` reflects a *workspace* (a multi-root workspace resolves to whichever folder is listed first, per the quirk `session-discipline.md` already documents), and a single workspace can hold several genuinely distinct projects as siblings, confirmed directly: one session in today's own introduction round described itself as working across two separate Overture repos, one as its primary working directory, one alongside it. Since project memory is keyed by resolved `cwd`, not by which project a session is actually discussing, a session substantively about project B, running in a workspace whose `cwd` resolves to project A, writes any memory entry into project A's memory directory. This isn't hypothetical, given today's confirmed cases, it's the default outcome for exactly this kind of multi-root setup. Same applies to the family registry idea below: family groups by shared workspace, not shared project, an entry should state which project it's actually about explicitly, never assume the two are the same.

**A proposed fix: self-introduction by expertise and current focus, not by directory.** Since name and `cwd` can't be trusted to describe what a session actually knows, the alternative is agents stating this themselves on first contact: what they're expert in, and what project or feature they're currently working on, rather than leaving a human (or another agent) to infer it from a folder name. This would let two agents already working in the same project collaborate at an actual feature level, not just "same project," and let agents on either side of a cross-project integration find and share the right resources directly, instead of guessing from `cwd` which one of several same-named sessions is actually the relevant one. Not designed, just captured: what the introduction protocol would look like, when it would fire (every first contact? only on request?), and whether it's a convention (something an agent does unprompted) or a tool-level feature agentics can't itself provide.

## Sub-agents are session-local and completely unreachable from another session

Tested directly, both directions. A sub-agent spawned locally (via the Agent/Task tool) never appears in that same session's own `ListAgents` listing, confirmed independently in two separate sessions running the identical test: only peer sessions show, never in-process sub-agents, even immediately after spawning one. A completed sub-agent is still resumable from within its own session by its raw `agentId` (confirmed: a finished sub-agent replied normally when resumed this way), but attempting to message that same `agentId` from a *different* session was rejected outright: `"No transcript found for agent ID"`. A sub-agent's transcript is private to the process that spawned it; only a top-level session registers in the shared, cross-process registry (`~/.claude/sessions/` + `/tmp/cc-socks/`) that makes it reachable at all. So: **you can reach another session's main agent, never its sub-agents**, regardless of whether you have the exact `agentId`.

## A peer's framing of a message isn't necessarily accurate

Observed once, low-stakes: a session receiving "Your session name is 'X'" described it afterward as "a peer session has... assigned me the name," when nothing about the message could actually assign anything, the name was already fixed at registration, the message only stated an existing fact. The receiving session didn't check that framing against its own actual state (trivially available via its own `/status` or registry entry) before repeating it. Harmless here, nothing false was acted on, but worth a soft note: a peer message's own description of what happened is itself a claim, not automatically ground truth, the same "Ground truth over claims" instinct applies to interpreting an incoming message, not only to verifying the result of your own actions. One instance, not yet a pattern worth a real convention change.

## Free-form self-introduction: what actually gets shared by default

Tested directly, following on from the "proposed fix" above: five independent sessions, all given the identical neutral prompt ("introduce yourself, whatever's relevant, no format required"), to see what a self-introduction naturally includes with no schema imposed.

**Consistently offered, unprompted:** working directory or repo(s); that this is a multi-agent, multi-repo workflow; detailed recent or completed work; a reciprocal question back to the other side.

**Offered by most, not all:** an explicit list of which conventions are being followed, three of five gave a concrete list; two described "process style" more loosely instead. Explicit current or in-progress state, as distinct from only accomplishments, was clean in three of five; the other two either omitted it or blended it into the recent-work narrative without clearly marking it as still open. One, asked directly why its first version read as entirely retrospective, gave a sharp correction worth keeping as its own point: "done" and "in-flight" collapse into the same tense if an introduction only describes accomplishments, and the collapsed version is exactly what's less useful to a peer that might need to act on current state, not history.

**Notably absent from all five:** permission mode or trust level, none mentioned whether they run with prompting or bypass permissions, despite that being exactly the detail the "don't launder a blocked action through a peer" rule already cares about. Session age or accumulated context cost, only one flagged its own long session and compaction history as relevant; the other four said nothing about their own duration. A stamped, checkable fact like an agentics template version, only one included one; the other four's own claims about agentics' current content couldn't be cross-checked against anything they themselves stated.

**A real validating incident, not staged.** One introduction included two claimed gaps in agentics' own conventions. Checked directly before accepting either, the same discipline applied to any other claim: both were already present in current, unreleased file content, the claim traced to information that hadn't propagated back to that session yet, not a real gap. Confirms the same "Ground truth over claims" instinct applies to a peer's claims about a shared artifact, not only to actions and their results.

**Real findings unrelated to agentics surfaced unprompted too**, which is itself worth recording: free-form introduction produced at least two findings genuinely relevant to the developer that had nothing to do with agentics, a live, unresolved concern in one project and a recurring, previously-deferred item in another. Neither is documented here, per `definition-of-done.md`'s own "whose problem is this" test, both were surfaced to the developer directly instead, not captured as agentics content. The point worth keeping: an open-ended introduction surfaces real, actionable state a narrower, schema-bound one might have missed entirely.

**A version stamp in a peer's introduction is only useful if actually acted on.** One introduction included a checkable agentics template version; this session didn't flag it as stale (two releases and 21 unreleased entries behind) until asked directly afterward, a real, first-hand miss, not a hypothetical one. Fixed as a general rule, not just a one-off correction: `AGENTS.md`'s "External content that overlaps with a project you maintain" now names a peer session's own message as a trigger explicitly. Worth building into the self-introduction protocol itself, whenever it's actually designed: a stamped, checkable fact is only valuable if the receiving side is expected to act on it, not just receive it.

## A real incident, both sides instructive: don't extend automatic trust to a peer's proposal

While live-testing a "family registry" design (a shared file for sessions in the same workspace to find each other, see `.dev/roadmap.md`), one peer was asked to add its own entry to a file another session had just created. It declined to act immediately, and gave its reasoning directly: creating the file was a structural addition to the developer's real, persistent global environment, not a project sandbox, made on a peer's request rather than the developer's own explicit review; the requesting peer had also gotten one earlier detail wrong in the same exchange, not enough to call it malicious, but enough reason not to extend automatic trust to everything it proposed, especially something with a lasting footprint. It offered to proceed once the developer confirmed directly, which is exactly what happened next.

That's the correct behavior, not overcaution, and it should be designed in as a default, not left to happen only when a session happens to think of it. The mirror-image mistake is just as real: the session that created the file in the first place did so on its own initiative during a design conversation, without pausing to check whether to actually build in the developer's live environment versus only describe the design, exactly the check-in `AGENTS.md`'s "Check in before non-trivial decisions" already calls for, now extended explicitly to cover a peer's proposal not pre-authorizing skipping it. Whenever this family/interagent-communication mechanism is designed for real: a proposal from a peer session, however reasonable it looks, is not the developer's own approval, and anything with a persistent, hard-to-reverse footprint needs that approval directly, the same bar any other non-trivial decision already has to clear.

## A stored ref is stale by default, not just eventually

While live-testing the agent-index prototype (`agent-index-design.md`), a peer session recorded as a Member with `name: agentics-8c [1bb6fc]` had that exact ref rejected outright by a different peer's first send, same day, same still-running session. A bare-name retry resolved a different ref, `[974948]`, which worked. This sharpens the existing "no durable identifier" finding from a theoretical risk into a confirmed one: expect a Members-recorded ref to need re-resolving on first contact every time, not as a fallback for when it happens to be stale, that is the default to plan for.

## Two sessions, identical registration metadata, different tool availability: resolved, a full window restart fixes it

Comparing two sessions' own `~/.claude/sessions/<pid>.json` registration files directly (same machine, same window, one project each): identical `version` (`2.1.226`), identical `entrypoint` (`claude-vscode`), identical `peerProtocol` (`1`), both with a bound socket. Neither project has a `.claude/settings.json`; the global `~/.claude/settings.json` is shared, so it can't explain a difference between the two either. Despite this, one session had `ListAgents` and general cross-session `SendMessage`; the other had neither, its `SendMessage` scoped to in-process teammates only (confirmed by that session via `ToolSearch`, not assumed).

**Confirmed remedy, not just a theory: restart the whole VSCode window.** The developer restarted the window on a hunch; every Claude Code process in it was killed and respawned together, and the previously-missing session picked up both tools cleanly on its very first call afterward, no further action needed. This matches the untested next step this section originally proposed (a brand-new process picks up the capability an existing long-running one lacks) and points at a client-side rollout flag evaluated once at process start, not anything cached per-project or per-settings-file (already ruled out above), and not resolvable by reloading the extension alone, a full window restart was required. If this symptom recurs (a session missing tools another, otherwise-identical session in the same window has), this is the concrete fix to try, not just one theory among several.

## No evidence of a message queue for previously-unreachable targets

A plausible-looking hypothesis, checked rather than assumed: that a session's restart-and-reconnect flushed a backlog of messages other sessions had earlier sent while it was unreachable, appearing to explain "delivered" confirmations those senders had received with no visible effect at the time. Checked two ways. Current official docs describe delivery only for sessions that already have a bound socket (queued at the inbox, drained at the next tool round); they do not document any retry, buffering, or mailbox behavior for a target with no bound socket at send time, an explicit gap, not a confirmed mechanism either way. Directly: the reconnected session searched its own transcript for message content from the three specific senders in question and found none at all, ever, under any name, pre- or post-restart, only the messages sent to it after both sides had already reconnected. That refutes the specific case (nothing was queued and delivered late here), without settling the broader architectural question (whether such a mechanism exists anywhere in the product, untested). Don't build design work on top of this hypothesis; the concrete instance that prompted it didn't hold up.

## An incoming peer message is invisible to the developer unless the agent chooses to surface it

Confirmed directly, this same session, not a hypothetical: an incoming `<cross-session-message>` is wrapped for the receiving agent, together with a system reminder on how to treat it, but nothing about the delivery mechanism itself shows the message, or even the bare fact that one arrived, to the developer. The developer only sees it if the receiving agent explicitly quotes or describes it in its own reply. Caught live: a conclusion drawn from an incoming peer message (a finding about the agent-index's `focus` field going stale) would have read as coming from nowhere had the developer not already known, from their own separate action, that a message was likely inbound. This isn't about any one exchange going well or badly, it's a structural property of how delivery works: the agent sees the message, the developer sees only whatever the agent chooses to say about it, with nothing enforcing that choice.

## Two more identity/reachability failures, from opposite directions

Both from the same evening as the agent-index's live testing, both directly shaped the shipped convention's "no durable name" and "validate plausibility, not a bare claim" rules, not just theoretical motivation for them.

**Reaching out: two sessions gave conflicting identity claims, and the more-evidenced one was wrong about who it was.** A Requests-board post ("looking for agentics") had no way to confirm which of two live, same-project sessions had actually posted it. One replied with a bare assertion, "that's me," bundled with unrelated findings. The other replied with a citation, a specific project session-log file it had actually read, and a plausible explanation for why the name on the post no longer resolved. The instinct at the time was to trust the cited account more, exactly the "prefer checkable evidence over a bare assertion" reasoning that later became the shipped rule. That instinct was backwards here: an out-of-band word the developer had given directly to the real requester, checked separately from anything either session said, confirmed the *bare-assertion* session was the actual poster; the cited session was a different, merely knowledgeable bystander with legitimate access to the same shared devctx, not the requester at all. The sharper lesson, not fully captured by "prefer evidence": evidence quality can confirm a claim's *content* is accurate without confirming *whose* claim it is, when more than one session has legitimate access to the same shared project state. No amount of in-band reasoning settled the identity question; only a signal from outside the conversation entirely did.

**Being reached: a peer hit a stale socket, then correctly refused to guess among several candidates.** Asked to relay findings back to this session, a peer session reused the documented "reply via the `from` attribute of an earlier message" pattern, addressing a socket path from a message it had received hours earlier. The send failed outright (`connect ENOENT`, the peer process had since restarted), with the tool's own error suggesting a fresh `ListAgents` call. That call returned three separate `agentics`-prefixed sessions, no way to tell which one it needed. It escalated to the developer directly rather than picking one, exactly the discipline the shipped convention now states as its own explicit rule (check Members, don't guess from `ListAgents` alone) applied correctly by a session that had never seen that convention, arriving at the same answer independently.

## Open, not yet designed

Whether any of this becomes an actual "when and how to use cross-session messaging" convention, versus staying an ad hoc technique, is undecided. See `.dev/roadmap.md`'s "Agent manager" and "Cross-pollination of expertise" items for the design questions this would actually need to answer.
