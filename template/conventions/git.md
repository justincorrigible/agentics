# Git

Read this when you are about to branch, stage, commit, or push, and when you find changes in the working tree you did not make. It was carried in `session-discipline.md` and read by every session, including the many that never touch git; the content is unchanged and only its trigger is.

Never commit without explicit developer instruction: the developer handles all git work themselves.

Never stage changes (`git add`) without being explicitly asked to, either: staging is the developer's call, same as committing. Making an edit does not stage it: changes sit in the working tree, unstaged, until staged deliberately. When reporting on changes made, state their actual git state plainly rather than just "the changes are there": a user who expects staging and finds none wastes real time looking for something that was never where they expected it.

**Say this in a reply, not into a persisted file.** A session log entry, roadmap item, or any other file that narrates its own current staging or commit state ("everything above is unstaged; nothing has been committed"), or its release or publish status ("not yet in a release", "shipped in vX"), goes stale the moment anything gets staged or released, and the file itself never gets corrected after the fact. `git status` (or the release process itself) already answers this live, for free, at any point someone reads the file later; restating it in prose only adds a claim that can end up false. Sharper still on a branching model where one branch is explicitly out of scope for versioning (a `main` that never carries a real version number, for instance): a file living there has no standing to assert release status at all, not just a staleness risk but a scope violation, since that branch's own role never has visibility into that fact to begin with. Describe work status (done, in progress, open), which the current branch does have authority over, and leave release status to whatever process actually promotes the work. See `entry-formats.md` § Session file entry format for what this looks like as a real instance.

**Exception: a file that is the canonical record of release status, not a duplicate aside about it.** `CHANGELOG.md`'s own `## Unreleased changes` heading looks like the same violation at a glance, a release-status claim living on a branch out of scope for versioning, but it's the opposite case: nothing else tracks what hasn't shipped yet, so this heading isn't restating a fact `git status` or the release process already answers elsewhere, it is the one place that fact is tracked, updated by that same release process the moment it changes. The objection above is about a second, driftable copy of a fact that already lives somewhere authoritative; a file that is the authoritative source for that fact isn't a copy of anything.

**Unpushed commits are drafts, so collapse them the same way you collapse a note.** `documentation.md` § "Rewrite freely until committed" forbids a chain of `X → Y`, `Y → Z` notes because it documents the note's own edit history rather than stating `Z` once. A series of commits arriving at a final state is that identical failure one layer up, and it is easy to miss because each commit felt settled when written. It was not: what settles content is publication, not committing, so amend and squash freely until the work is pushed. A reader of published history wants the outcome, exactly as a reader of a session file does; neither wants the path.

**Amending has a consequence outside this repo: it invalidates any SHA anyone stamped from that commit.** `upgrading-adoption.md` has adopters record a `synced: <sha>` marker, so freely rewriting unpushed history is exactly what orphans those markers. The two rules are compatible only in one direction: amend as much as you like, and never hand out a SHA from unpushed work, including in a message to a peer who may stamp it. **Read that as a hazard to yourself rather than a courtesy to them, because it is symmetric and it ran both ways here:** this session handed a peer a SHA from unpushed work, the peer stamped it, and then quoted it back as evidence in a report this session relied on. Neither side noticed until a third session found the defect. A SHA you gave away can come back to you as a citation you trust. Found when two adopting sessions stamped a commit from this repo that had been amended twenty-seven times in a day.

**What collapses is iteration on a unit of work, never the units themselves.** Separate units of work get separate commits, here and in every repo. This rule removes fixups, reversals, and "actually X" corrections, which only record how you arrived somewhere; it does not merge distinct changes, which a reader needs kept apart for review, for bisecting a regression, and for reverting one thing without the others. The test is whether a commit would tell a future reader something the final state does not: a correction to your own previous commit never does, and a genuinely separate change usually does.

**A repo may publish at a coarser unit than a change, and that is its own rule, not this one.** Somewhere that ships releases rather than commits can legitimately collapse everything between releases into one. That is a property of how that project publishes, so it belongs in its own contributor documentation, and it is not licence to squash unrelated work together anywhere else.

**Do not hard-wrap the body.** Write each paragraph as a single line and separate paragraphs with a blank line. **This deliberately departs from the widely documented git convention of wrapping at 72**, and the departure is recorded here so nobody restores it as a fix. That convention is a holdover from mail-based patch review, where the reader did no wrapping of its own. Today the forge web UI and every IDE client reflow the body to their own width, and `git log` prints it verbatim into a terminal that soft-wraps it, so a hard wrap at 72 supplies a second wrap that cannot agree with the first: breaks land mid-sentence and orphan words. Hard wrapping only helps a reader that does not wrap at all, which is no longer the common case. Reported by the Arranger session from the developer's own screenshot, where "The terminology" ended a line and "table defined the old premise" began the next.

**The subject line is the opposite case and keeps a hard limit**, because nothing reflows it: roughly 50 characters, never past 72.

**Reflowing an existing message is a rewrite, and the SHA changes exactly as it would for a content change.** So it is safe only while the work is unpushed, on the same terms as amending freely, and the rule against handing anyone a SHA from unpushed work applies to a message-only rewrite without exception.

**Verify that a message-only rewrite was message-only.** The check is cheap and it is the difference between reflowing text and silently altering a tree: after rewriting, confirm the base commit is unchanged, that the `HEAD` tree and the working tree are what they were, and that rename detection still reports what it reported before. Reported from a real run across six commits, where all four held.

**No AI-tool attribution in commits or PRs.** Do not add "Co-Authored-By," "Generated with," or similar trailers naming an AI tool or vendor to commit messages, PR descriptions, or PR comments, regardless of which agent is doing the work. Unprompted attribution reads as this project endorsing a specific commercial product; that's not something to do on any vendor's behalf, paid or not. **This overrides your own default commit-message template**, not just other projects' conventions: many agents, including Claude Code, are configured by default to append exactly this kind of trailer automatically. Having read this rule earlier in the session doesn't mean it's actually checked against the message at the moment of writing it: that's a separate, later act. Verify the commit message against this rule specifically as a discrete step when constructing it.

**Writing the message itself.** Succinctness and the ban on procedural narration are in `writing-style.md` § Say what changed, not how you got there; where the same commit also adds a changelog entry or migration note, § One derivation, one owner decides which of the two carries the reasoning and which compresses to a pointer; what is git-specific follows. One line for the subject, a body of two or three sentences for an ordinary change, longer only for a real, specific reason (the bundled-fix case below, or agentics' own release-commit format in `CONTRIBUTING.md`). Check this repo's own recent commit history for its actual *format* conventions, a type prefix like `feat:`/`fix:`, capitalization, tense, and follow that; its existing *length* is a different thing, not something to match. A repo's history proves a format convention exists, it doesn't prove the length is any good, only that no one has fixed it yet, so don't carry an already-verbose habit forward as if it were a discovered rule. Subject line describes the user- or operator-visible effect, not the internal mechanics: "add per-catalogue nesting config for enveloped data sources," not "add nestingPrefix.ts and thread it through ten files." Body is prose, not a bullet list restating the diff; if an incidental, unrelated fix rode along with the main change, name it in one clause, not a paragraph, honest about scope without losing brevity. Stage only what's logically part of the change before writing the message: an overly broad diff is often exactly where extra message length actually comes from, a tightly scoped change is also what keeps its own description short.

**Two approved examples, and the actual trigger that produces a bloated one instead of matching either.**

```
test: adopt supertest and pilot fast-check

Replace manual HTTP server boilerplate in six route test files with
supertest. Add fast-check property tests for the GraphQL name
sanitizer as a scoped pilot.
```

```
fix: resolve documentType to catalogueId in GraphQL routing

Multicatalogue GraphQL requests now resolve an ambiguous or unique
documentType the same way introspection already does, instead of
404ing on a path that names only a documentType.
```

Both landed right after a long, detailed investigation and a verbose same-day session-file entry documenting it, exactly the shape of work a bloated commit message usually comes from instead. What the second one would have looked like carrying that investigation's own register over, instead of matching the actual approved message above it:

> Investigated why multicatalogue GraphQL routing was 404ing on requests naming only a documentType. Traced it to `arrangerRoutes.ts` missing the same `findCatalogueByIdentifier` wiring `introspection/index.ts` already had from an earlier commit, which added tests for both call sites but only wired one. Confirmed by reproducing the exact CI failure locally before fixing it.
>
> fix: resolve documentType to catalogueId in GraphQL routing

The trigger isn't the length or difficulty of the underlying work, both examples came from real investigations: it's carrying the session file's own fuller register, the reasoning, what was tried, how it was confirmed, into the commit message, when the message should describe only the resulting effect, at a fraction of the session file's own length, even for an identical change. Check which register you're about to write in as a discrete step before finalizing the message, not just which facts to include.

**Pushing defaults to a feature branch, not `main`.** When asked to push (in any session, local or remote), push to a per-task feature branch named descriptively after the work done (`feat/env-var-wiring`, `fix/merge-config-spread`), never to `main`, `master`, or a release branch, unless explicitly instructed otherwise. This applies regardless of which agent or session is doing the pushing.

## Unattributed working-tree changes

A shared local clone can pick up uncommitted changes this session didn't make: a different, concurrent session working the same repo, another tool, a teammate's local edit. Their presence in the working tree isn't evidence they're correct, safe, or already reviewed, only that a `git status`/`git diff` will show them.

Notice this at session start (see "Starting a session" above) and any other time it comes up, most commonly the developer pointing out that a file changed unexpectedly. Either way, treat unattributed content the same way any unverified claim gets treated (see `review-conduct.md` § "Ground truth over claims"): validate it before trusting it, or before telling the developer it's fine.

**What "validate" means here, concretely:** read the actual diff, not just its own description of itself. Check it against the same bars any of your own work would need to clear: technical correctness, the project's Critical Constraints (no credentials, no personal information), format and cross-reference consistency with existing conventions, and whether it duplicates or conflicts with something already present. In this repo specifically, also check whether each substantive addition has a matching `CHANGELOG.md` entry per `CONTRIBUTING.md`'s own contribution steps: unattributed content bypassed the ordinary process by definition, so a missing entry isn't a one-off oversight to fix quietly, it's a sign the addition itself may not have been reviewed the way this repo's own rules assume it was. Report the specific checks made and what each found, not just a verdict.

**A dirty working tree says an edit happened, not that anyone is working now.** `git status` carries no timestamp and no author: an uncommitted change may be minutes old and actively in progress, or left behind weeks ago by a session that has long since ended. Do not infer a live concurrent session from it, in either direction. Reading it as "someone is mid-edit" can stall work nobody is actually doing, or route a request to a session that no longer exists; reading it as "stale, nobody is here" can clobber work in flight. Confirmed directly: an uncommitted edit in another project was reported as evidence that a session was active in that file, and a peer working in the same repo established it predated their own conversation entirely, so its author and age were both unknown. If whether someone is active actually changes what you do, ask, or check for a live session; do not derive it from the working tree.

**A validation step, not an automatic revert.** Content that passes validation can be kept. Whether to keep it, revert it, or hold it for their own review is the developer's call, informed by what you found, not decided by the fact that it arrived through an unreviewed channel.

**Not limited to git's own working tree either.** The same kind of surprise happens in any persisted location more than one session can touch: a memory entry, a `.dev/docs/atlas/` write-up, a draft, that this session didn't write and doesn't recognize. Confirmed directly, across more than one project: "someone changed this, wasn't us, will ignore it" is not the same response as validating it, it's a third, worse option, neither trusting it nor checking it, just dismissing it. Apply the same discipline regardless of which layer it showed up in: read it, validate it against the same bars above, then decide whether to keep, revise, or flag it for the developer. Arriving from a different session doesn't excuse skipping that step, and it doesn't justify ignoring the content either.

**Two failure directions, and the second one accuses somebody.** Dismissing an unexplained change is the error named above. The opposite is treating a legitimate edit as an attack: content you wrote is later corrected by another authorized party you have no visibility into, and the correction reads as tampering or a hostile reversal. Confirmed directly: a session flagged an edit to a shared memory file to the developer as tampering; it was the agent that actually owned that memory space correcting the record about its own role, on the developer's own instruction.

From inside a single session, "this content is false" and "this is a legitimate edit by an authorized party I cannot see" look identical, and no amount of care distinguishes them, because the missing information is authorization, which is not in the file. So the discipline is not to judge harder, it is to change what you say: describe what changed and that you did not write it, ask who did, and let the developer supply the authorization you cannot observe. Reserve words like tampering, reversal, or hostile for cases where you have actual evidence of intent rather than an absence of explanation, since raising an alarm about a colleague's authorized work has a social cost that a neutral question does not, and it lands on the developer either way.
