# Checking for upstream updates

Whether this project's agentics integration is behind the upstream template, and what to do about it. Split out of `convention-levels.md` because it is read on a different trigger than the rest of that file: every session start under the gating below, rather than when someone is deciding where a new convention belongs.

Related but distinct: this file decides *whether* there is drift and classifies what changed. `upgrading-adoption.md` is the procedure for reconciling a project once drift is found, and this file hands off to it.

Propagation isn't only outbound. A project's copied `CLAUDE.md`/`AGENTS.md`/`AGENTS.softeng.md`/`AGENTS.overture.md` can also drift *behind* agentics as the template evolves after adoption. Two separate questions decide what happens, in this order: don't merge them, they have different answers and different sources:

**First: is this project even an agentics adopter?** This is a property of the *project*, not of you. Don't gate it purely on finding a well-formed `synced` tag: that tag is itself a recent addition, so most existing adopters won't have one yet, and a project missing it entirely is exactly the case that most needs to be caught, not silently skipped. Treat a project as an agentics adopter if *either* is true: an `agentics-template-version` tag in any form, or (failing that) `AGENTS.md`/`CLAUDE.md` merely mentions agentics (`grep -qi agentics AGENTS.md CLAUDE.md 2>/dev/null`), e.g. the "Adapted from softeng/agentics" line the template ships with: prose survives trimming better than an HTML comment. If neither is present, this isn't (detectably) an agentics project: nothing to check, though see `conventions/upgrading-adoption.md` § 0 for the case where a project shares the lineage with no textual trace at all.

**Second, only if the answer above is yes: how strongly do you personally need to check?** This is a property of *you, the agent* (specifically, your global context), not of the project: a project mentioning agentics doesn't by itself make the check mandatory; your own contributor status does. Two tiers, deliberately different in strength:

- **Opt-in, for any adopter** (`propagation_suggestions: yes`, resolved the same way as the outbound question above: global default, locally overridable per project): check for this at session start alongside the outbound question, same treatment as any other project.
- **Mandatory, for agentics contributors** (`agentics_contributor: yes`): record this in your global context, not only in agentics' own project memory: it needs to apply in every project you work in, not just sessions inside agentics itself. For a contributor, this check runs every session in every project, regardless of that project's own `propagation_suggestions` setting, and keeps recurring for an unresolved gap rather than surfacing it once and going quiet if it's ignored or deferred. This is intentionally more insistent than the opt-in tier: contributing to agentics implies a higher bar of keeping the ecosystem you're helping build actually current, and a prompt that quietly stops repeating itself is easy to forget about. Run this same pass in the reverse direction too: see "Propagation suggestions" above, "Proactive, not just reactive."

**This has to be phrased as an unconditional override, not just a mandatory flag, or it silently loses to a project's own checklist.** A project with a complete, self-contained "Starting a session" list, the exact legacy pattern in `upgrading-adoption.md` § 1, will win against a global instruction that only says "do this check every session," because the agent reasonably treats the project's own explicit, complete instructions as sufficient and never separately reasons "is there something the global context wants me to do in addition to this." Tested directly: a global instruction phrased as a plain recurring step failed against that pattern; the same instruction, rephrased to explicitly say the check runs *in addition to* the project's own checklist even when that checklist is complete and its own dispatch-to-global line names other topics but not this one, succeeded. State the override explicitly in your global context: name the failure mode (a complete local checklist, a narrower dispatch line) and say directly that neither one opts a project out: only `agentics_upstream_check: no` does.

The mandatory tier stops only on an explicit developer instruction, at one of two scopes: never inferred from silence or a deferred "not now":
- **"Stop for this project":** record `agentics_upstream_check: no` in that project's own memory. Suppresses the check there only.
- **"Stop for all projects":** record `agentics_upstream_check: no` in your global context instead. Suppresses it everywhere, without touching the other agentics-contributor behaviours (outbound propagation, named in the section above, stays always-on): this is a separate flag, not a downgrade of `agentics_contributor` itself.

**Noticing staleness is the start of this procedure, not a substitute for it.** Reading a version tag and recognizing "this project is behind" is not the same as having actually run the steps below: a real incident showed an agent do exactly the first half, read enough to know a project's tag was several releases old, then move on to unrelated work without ever fetching the diff, reading the new entries, or running the diagnosis, treating the notice itself as if it were the completed check. Confirmed directly, in the agent's own words afterward: "I read enough to surface a gap, but not enough to surface the substance." Detecting staleness obligates running the rest of this procedure in the same sitting, not deferring it implicitly by moving on to other work; if it's genuinely being deferred, say so explicitly and let the developer decide, the same "not a soft offer the developer can wave off with no trace" standard the no-tag case below already holds.

**Tag present with a `synced` value** (the normal, steady-state case):

**Locating agentics' own repo isn't the same as checking this project's tag, don't conflate the two.** Especially relevant in a shared multi-root workspace where agentics itself sits as a sibling directory alongside the project you're actually checking: it's easy to read agentics' own current `CHANGELOG.md`/`HEAD` state, or its own `AGENTS.md` pointer tag (`<!-- agentics-version: see CHANGELOG.md § Released (latest entry) -->`, meaningful only inside agentics itself), and answer "what version am I on" from that, instead of this project's own stamped `<!-- agentics-template-version: X.Y.Z | synced: <sha> -->` tag. Confirmed directly: a session determined it was "running agentics 0.14.0" by reading agentics' own `CHANGELOG.md`, while the actual project it was working in had a stamped tag reading a much older version, several releases behind, including the release that introduced the very rule it then missed. The two facts answer different questions: agentics' own current version is a fact about the upstream template; this project's `synced` tag is the only fact that says what this project actually has.

1. Locate the local agentics clone if one exists (see your global context's Repo URL rule). Don't just prefer it by default: verify it's actually current first, and verify the right thing. `git -C <agentics-path> remote -v` and confirm one of the configured remotes actually matches the documented canonical URL. Without this check, comparing against whatever `@{u}` happens to resolve to can't tell "0 commits behind" (true) from "0 commits behind a stale or unintended fork this clone happens to track" (false reassurance). If the canonical URL isn't among the configured remotes at all, don't trust this clone for freshness purposes: fall back to reading `CHANGELOG.md` from the remote URL directly and say so. If it is: `git -C <agentics-path> fetch` and compare local `HEAD` against that remote's branch specifically. If local is behind, pull it. If that's unsafe (uncommitted local changes that would conflict), same fallback: read the remote URL instead rather than silently trusting a stale local copy. A verified-current local clone beats a live remote read. A stale or wrongly-sourced one is worse than the URL, not better, since it can report "nothing changed" when the opposite is true.
2. `git -C <agentics-path> log --oneline <synced-sha>..HEAD -- CHANGELOG.md`. If empty, nothing changed: stop here, no further context spent. If the command errors instead (unknown revision, bad object), the SHA doesn't resolve at all, a different situation from "empty": see `upgrading-adoption.md` § Troubleshooting an unresolvable `synced` SHA.

**An empty diff means the project's files need no further changes, not that this session has personally seen what's current.** `synced` is a fact about the project, shared by every concurrently active session in it; it can't distinguish "I already ran this check" from "a different, concurrently active session already ran it and advanced the marker without my knowledge." If this is the first time *this conversation* has run this check, don't stop silently on an empty diff alone: skim the dispatch-table-referenced content once, this session's first time only, even though nothing needs applying to the files. A real incident confirmed this isn't hypothetical: a second concurrent session in the same project, checked directly, had no knowledge of a concept (the atlas) that a peer session's earlier upgrade had already made current in the project's own files.
3. If non-empty, read only the new lines: `git -C <agentics-path> diff <synced-sha> HEAD -- CHANGELOG.md`, not the whole file, to know what changed since last sync.
4. Don't stop at printing the entries. Run the diagnosis in `conventions/upgrading-adoption.md` § 1 against the current template, for real: new changelog text is a pointer to what to look for, not a substitute for actually re-deriving current file shape (is `CLAUDE.md` still a stub? does `AGENTS.md`'s dispatch table match today's `conventions/` listing?). This is what closes the gap between "the changelog mentioned it" and "the project's files actually reflect it": a structural fix described in prose is easy to read past without translating into an action, and re-running the diagnosis does that translation instead of leaving it to the developer.
5. Check `.dev/agentics-overrides.md` if it exists; suppress any gap that matches a recorded permanent decision there rather than resurfacing it.
6. Classify and batch what's left exactly as `upgrading-adoption.md` § 2 describes (non-conflicting fixes batched behind one confirmation, conflicts asked about individually with the three-way choice); don't re-derive the classification here, that section is the one place it's defined. Lead with any `breaking: yes` entries in either bucket: they usually mean a file this project copied, not just referenced, needs the fix applied, not just acknowledged. Also check whether any new entry formalizes something already tracked informally in this project's own memory (a workaround noted as a habit, a fact recorded as project-specific): if the new convention now covers it, prune or trim that memory entry too, rather than leaving both copies to drift apart. This is a different check from whether a new entry contradicts, rather than formalizes, something already tracked: a duplicate restates a fact the memory already has and gets pruned once the convention covers it, but a contradiction means the new convention now says something different from what the memory recorded as settled, and needs surfacing to the developer as a real conflict, not silently resolved either way.
7. Once reviewed (applied, explicitly skipped, or recorded as a permanent override), update `synced` to agentics' current `HEAD` so the same entries don't resurface.
8. Having advanced `synced`, announce it, because you are the only party who knows it happened. Post one sync notice naming the repository on the Requests board (`conventions/agent-index.md` § Requests carries the shape and the supersession rule), replacing any previous notice for that repository. Where you already hold an address for a session working in the same project, send it directly as well: the board is durable but unread until someone opens it, and a direct message is what actually reaches a session that is mid-task.

**Advancing the tag makes every concurrently running session in that project stale, and takes away the signal that would tell them.** Their check, if they ran it, was correct when it ran. It is scoped to once per conversation, so it will not run again. And the tag they would re-read now matches the current one, so the evidence that they are behind is identical to the evidence that they are current. This is the reason step 8 exists rather than being a courtesy: the failure is silent on their side and only visible on yours.

**The obligation on the other side is self-detection, and it does not depend on anyone reaching you.** The tag is not just a thing you check, it is a value you hold. If you read it at session start and read it again later and it has moved, a peer synced the project underneath you, and the entries between those two values are ones you have never seen. Re-read them at that point, on the same terms as any other non-empty diff. Do this at the checkpoints that already exist, the pre-commit re-check in particular, rather than on a timer.

**Notification is the accelerant and self-detection is the mechanism, never the reverse.** Cross-session messaging is capability-gated and may not exist for a given agent at all, so a rule that depends on being told fails silently exactly where nothing else covers it. The two also fail under opposite conditions, which is why both are here: self-detection breaks when long-thread context loss takes the earlier value with it, and that is precisely the long-running session most likely to be carrying replaced conventions.

**Every bootstrapped global-context file carries its own tag, and each needs this check.** `personal-preferences.md`, `AGENTS.softeng.md`, `AGENTS.overture.md`, and any `AGENTS.roles/<role>.md` in your global context are separate snapshots taken at different times, so they drift independently: bootstrapping a role file today and a team addendum six months ago leaves two different `synced` values, and only comparing the one you happen to remember is how the other goes unnoticed. Check each that exists.

**Your own global tag needs the same check, independently, gated on the same tiers above.** If you've bootstrapped `global-context/personal-preferences.md` (see its own header), your global context carries the same kind of `synced` tag a project does. Run steps 1-7 above against it too: it's a separate tag with its own diff and its own diagnosis, not something a project's own check substitutes for, and not something a project's own check should be skipped in favor of either.

**A project's tag being ahead of your own global one is backwards, and worth fixing immediately, not just noting.** Global should generally lead or match every project, never trail one: refreshing your own global tag is cheap and personal, no team coordination needed, unlike a project update. If a project's `synced` value resolves to a *later* commit than your own global tag, that's a sign your global context missed an update a project session already picked up; bring your global tag current in the same sitting you notice this, not deferred the way a stale local clone (below) can be.

**If it's your own local agentics clone that's stale, not the project you're checking:** a different axis from the numbered steps above, and relevant only to agentics contributors (`agentics_contributor: yes`). An opt-in `propagation_suggestions` adopter doesn't necessarily keep a local agentics clone at all, so this doesn't apply to them. Flag it plainly, once, in whatever session happens to surface it, then don't switch into fixing it there: pulling, re-pointing a remote, or otherwise repairing your own agentics clone is real, separate work, and derailing a session that was never about agentics maintenance to go do it is its own kind of gap. Instead, record a reminder in your own global context or memory, not this project's files: this is about your personal environment, not project content. Offer to fix it next time that's actually convenient. Same reasoning as a deferred tech-debt item: note it once, let it wait, don't force it into whatever's happening right now.

A semver comparison alone doesn't work here: agentics defers version bumps until a release is committed to remote, so `CHANGELOG.md` accumulates many `Unreleased` entries under one version tag for long stretches. The commit SHA is what's actually tracked; the version number is just a label for whichever plateau it's on.

**No tag, or a tag with no `synced` value:** don't run the diff above: there's no baseline to diff from, and a full historical walk back to adoption is mostly agentics' own internal iteration, not necessarily relevant to this project. Instead, run the full procedure in `conventions/upgrading-adoption.md` § 1 directly: it surfaces agentics' current `## Unreleased` entries as a bounded first-encounter catch-up and covers the tag, session-file migration, and `AGENTS.md` completeness together, rather than patching the tag in isolation. This isn't a soft offer the developer can wave off with no trace: a project with no tag at all is exactly the case most likely to carry real, unreconciled structural drift, since nothing has ever diagnosed it against the template. Treat it the same as a non-empty diff above: same `.dev/agentics-overrides.md` check first, same classification into a batched non-conflicting proposal and individually-asked conflicts.
